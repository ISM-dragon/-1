# ISM Master Technical Debt

**Audit date:** 2026-08-19
**Scope:** Current repository baseline and the production-hardening package.

## Findings

| Priority | Path | Problem | Why it matters | Proposed fix | Dependencies | Acceptance criteria |
|---|---|---|---|---|---|---|
| P0 | `gateway/main.py`, deployment configuration | Remote authentication is optional unless `REQUIRE_GATEWAY_TOKEN=true`. | An accidentally exposed Gateway can accept private operations without a session token. | Require the token in production deployments and fail health/readiness when a remote deployment has no configured token. | Deployment environment and secret provisioning. | Production startup/readiness reports a configuration failure; authenticated routes reject missing or invalid bearer tokens. |
| P1 | `gateway/main.py`, `gateway/worker_queue.py` | Gateway-side processing state is durable, but transition history, persistent cancellation, and attempt metadata are incomplete. | Restart and worker-crash behavior is difficult to audit and cancellation can be lost across process boundaries. | Add `processing_job_transitions`, canonical stage/state fields, retry metadata, and a cancellation marker; resume from pipeline checkpoints. | SQLite migration and worker termination policy. | Every transition is persisted; cancelled jobs are not requeued; retry/resume are idempotent and tested. |
| P1 | `gateway/main.py` | The public API has no canonical session endpoint and no stable publishing-job resource routes. | Android and desktop clients must use platform-specific legacy routes and cannot share a versioned contract. | Add `/v1/auth/session`, `/v1/social/accounts`, `/v1/publishing/jobs`, and documented error envelopes while retaining compatible routes. | Client migration and OAuth provider adapters. | Contract tests cover successful and failure states, authentication, validation, and idempotency. |
| P1 | `gateway/main.py`, source upload | Upload accepts a raw request stream but has limited media validation before a job is created. | Invalid or non-video data can consume storage and fail late in the pipeline. | Enforce content type/extension, size, optional ffprobe validation, and safe cleanup. | FFmpeg/ffprobe availability and policy for browser uploads. | Invalid media is rejected with a stable error code and no orphan directory remains. |
| P1 | `gateway/worker_queue.py` | The in-memory queue deduplicates only within one process. | Multiple Gateway replicas could claim the same durable job. | Keep single-owner deployment explicit or add a DB lease/claim token before horizontal scaling. | Deployment topology decision. | A concurrent-claim test proves only one worker owns a job. |
| P2 | `pipeline/tests` | Tests require running from `pipeline/` or setting `PYTHONPATH`; root-level collection initially failed. | CI and contributors can receive false failures unrelated to product code. | Add pytest `pythonpath` configuration and a documented root command. | Pytest configuration. | `python3 -m pytest pipeline/tests -q` works from repository root. |
| P2 | `android/app/build.gradle.kts` and package declarations | The source namespace still contains `com.example` compatibility identity. | Store identity and future migrations can diverge from the ISM product identity. | Define an intentional namespace/application ID migration plan and keep old installs supported until a release boundary. | Android package migration and deep-link review. | CI checks identity consistency; release notes document the migration path. |
| P2 | `app`, `android`, `gateway`, `pipeline` manifests | Version values are present in multiple manifests. | Drift can make clients report incompatible API or release versions. | Add a generated/version-check script and CI assertion against a single canonical version file. | Release workflow. | CI fails on product/version/API mismatch. |
| P2 | `gateway/main.py`, provider registry | Capability registration and health are implemented, but the full task-to-capability fallback policy is not yet the single execution path for every AI task. | Provider key presence is not equivalent to capability readiness. | Route every structured AI task through the registry with schema and provenance records. | Provider-specific adapters and usage accounting. | Health probes exercise required capability; primary/fallback/degraded outcomes are persisted. |
| P2 | Pipeline virality and calibration modules | Score explainability and deterministic pipeline components exist, but outcome calibration is not a complete production closed loop. | Users cannot distinguish an uncalibrated prediction from a measured one. | Version predictions, outcomes, score versions, and calibration models; expose `calibrated=false` when evidence is absent. | Analytics provider data and schema migrations. | Golden score fixtures and calibration regression tests pass. |
| P3 | UI surfaces and localization | Arabic/English RTL and a unified health indicator are not consistent across all desktop and Android screens. | Technical failures are harder to understand and accessibility suffers. | Centralize error mapping, localization keys, and readiness states. | Product copy review and Android resource migration. | Loading, success, error, retry, offline, auth, and processing states have accessible labels. |
| P3 | Release workflows | CI covers selected desktop/Android workflows but not the full end-to-end import-to-analytics path. | Build success does not prove the production workflow. | Add fixture-based Gateway/pipeline smoke tests and provider-blocked reporting. | Deterministic media fixture and non-secret test credentials. | CI produces artifacts and an explicit list of external tests not run. |

## Baseline evidence

The initial Gateway suite passed **29 tests**. The desktop TypeScript/Vite build passed. Pipeline test collection initially failed because the package was not importable from the repository root; this is corrected in the packaging/test configuration. Android Gradle tooling is available, but Android tests must run from the `android/` directory.

## Prioritization

P0 items are deployment blockers and must be handled before exposing a Gateway to the public internet. P1 items affect correctness, security, or recoverability. P2 items are required for production completeness but can be delivered behind the stable API contract. P3 items are polish and usability improvements that should not displace reliability work.
